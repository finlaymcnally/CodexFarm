# Codex exec upstream reasoning surface investigation report

## What this report is for

This report is meant to be handed to an external search-oriented AI that cannot see this repository or my local machine. It explains exactly what was investigated, what was observed locally, what is known about the likely upstream reasoning surface, and why I still cannot claim there is a reliable way to harvest that reasoning from current standalone `codex exec` runs.

This report is intentionally detailed. The goal is to give the next investigator enough context to research the upstream Codex CLI / API behavior without needing access to this codebase.

## Bottom line first

I found a strong upstream candidate surface for real Codex reasoning:

- local Codex session artifacts under `CODEX_HOME/sessions/YYYY/MM/DD/*.jsonl`
- those files contain `response_item` records with `payload.type = "reasoning"`
- those reasoning items often include human-readable `summary_text`
- those reasoning items also include `encrypted_content`

However, I could not confirm a reliable way to harvest that surface from **current standalone `codex exec` runs** because:

1. Current `codex exec --json` on this machine emits no reasoning records on stdout.
2. A direct authenticated standalone `codex exec` probe did not leave behind a new standalone session artifact for the returned thread id.
3. That probe emitted stderr errors suggesting the rollout/session recorder failed:
   - `failed to record rollout items: failed to queue rollout items: channel closed`
4. The richer reasoning payload appears encrypted at rest (`encrypted_content`), so even where the upstream artifact exists, the full content is not plainly harvestable by a downstream tool unless Codex or the API provides a supported decryption or summary surface.

So the practical answer is:

- the upstream reasoning surface appears to exist
- but I do **not** have evidence that current standalone `codex exec` reliably persists that surface in a way CodexFarm can depend on

## Why this matters for CodexFarm specifically

CodexFarm is a local Python tool that shells out to `codex exec` in non-interactive mode and persists telemetry artifacts for each call. The current bug is not about interactive CLI rendering. The bug is about what downstream automation can truthfully capture and persist.

The original problem that triggered this investigation:

- CodexFarm `.trace.json` files often show no reasoning trace at all
- some rows previously showed fake reasoning counts because CodexFarm was heuristically matching words inside final output payload text
- that heuristic bug has already been removed locally
- the remaining question is: where is the **real** reasoning trace that the user sees in the Codex CLI?

The reason I needed to answer this precisely is that CodexFarm should persist the real upstream trace if it exists, but should not fabricate it.

## Why I cannot call the current standalone exec reasoning surface reliable

This is the core answer the next investigator should understand.

### Reason 1: stdout is insufficient

For the actual authenticated standalone probe, stdout only had:

- `thread.started`
- `turn.started`
- `item.completed` with `agent_message`
- `turn.completed`

There was no reasoning event on stdout at all.

That means CodexFarm cannot get the real reasoning trace from the public stdout JSON stream alone in the current observed setup.

### Reason 2: the richer upstream artifact exists historically, but did not reliably appear for the standalone probe

Historical session files absolutely show reasoning artifacts.

But for the exact successful standalone `exec` probe I ran:

- I got a `thread_id`
- I got a final answer
- I did **not** get a confirmed corresponding standalone session artifact

This is the biggest blocker.

A downstream tool can only harvest a side artifact if:

1. that artifact is actually created for the call
2. it can be found deterministically
3. it can be correlated to the right run without races

I could not prove any of those three for current standalone exec.

### Reason 3: stderr suggests recorder failure

The probe’s stderr repeatedly said:

- `failed to record rollout items: failed to queue rollout items: channel closed`

This is a major clue.

It suggests that:

- the CLI may indeed have an internal recorder for rollout/session items
- that recorder is not functioning or not staying attached in this standalone exec path
- the absence of a session artifact may be an internal failure, not simply “no reasoning existed”

Because of that, I cannot responsibly say:

- “the session artifact is definitely written and you can harvest it”

The local evidence points the other way.

### Reason 4: even where the artifact exists, the full reasoning payload is encrypted

In historical session files, reasoning records contain:

- `summary`
- `encrypted_content`

The important limitation is that the richer payload is not plain text.

That means there are really two different upstream surfaces:

1. a potentially human-readable summary surface:
   - `payload.summary[*].text`
2. an encrypted full reasoning surface:
   - `payload.encrypted_content`

If the user wants the same short “thinking blurbs” the CLI shows, the summary surface may be enough.

If the user wants the full internal reasoning content, I have no evidence that CodexFarm can decrypt or access it directly from local artifacts.

### Reason 5: summary presence is inconsistent

In historical session artifacts:

- some reasoning items had populated `summary`
- some reasoning items had `summary: []`

That means even if CodexFarm could harvest session reasoning items, it might still not always get a human-readable summary text for each reasoning step.

So the harvest contract would still be inconsistent unless the upstream product guarantees summary population.

### Reason 6: fresh-home behavior is also not enough to build confidence

The fresh-home probe showed:

- no session JSONL file
- only SQLite stores
- but the run was unauthenticated and failed early

That does not prove anything useful about reasoning capture in a clean supported standalone exec path.

It only reinforces that the artifact layout is not simple enough to assume.

## Most likely current reality

My best current model is:

1. Codex has an internal richer event/rollout/session stream than the public `exec --json` stdout.
2. Interactive or session-backed usage often persists that richer stream under `CODEX_HOME/sessions/...`.
3. That richer stream includes reasoning records with:
   - optional human-readable `summary`
   - encrypted richer reasoning content
4. Current standalone `codex exec --json` in this environment either:
   - does not reliably persist that session/rollout artifact, or
   - tries to but fails in this mode, as hinted by the `channel closed` recorder errors.

That is why I can say “I found the likely upstream surface” but **cannot** say “CodexFarm can reliably harvest it right now.”

## What an external search AI should research

The next investigator should focus on upstream Codex CLI / OpenAI research, not this repo.

Questions to answer:

1. In current Codex CLI versions around `0.114.0`, is standalone `codex exec` supposed to persist a rollout/session artifact under `CODEX_HOME/sessions/...`?
2. What exactly does the error
   - `failed to record rollout items: failed to queue rollout items: channel closed`
   mean inside the Codex CLI implementation?
3. Is there a known regression where `exec` no longer writes the richer session artifact even though interactive runs do?
4. Is there a hidden config, environment variable, or feature flag that enables session/rollout persistence for exec mode?
5. Has the richer reasoning surface moved from session JSONL into SQLite in newer versions, and if so:
   - which table
   - which schema
   - how to correlate rows to a standalone exec invocation
6. Is there a supported way to ask the API/CLI to return reasoning summaries or encrypted reasoning content for non-interactive runs?
7. Does current `exec --json` intentionally omit reasoning from stdout, or is that a regression from older versions?
8. Is there any supported way to retrieve reasoning summary text after the fact by thread id?

## What a reliable solution would need to prove

Before CodexFarm should depend on any upstream reasoning surface, the next investigator should be able to demonstrate all of the following:

1. Run a standalone `codex exec` call.
2. Show where the reasoning artifact is written.
3. Correlate it deterministically to that exact invocation.
4. Show what part is plain text versus encrypted.
5. Show whether summary text is always, sometimes, or never present.
6. Show whether the artifact is created on success, timeout, nonzero exit, and auth failure.
7. Show that the behavior is stable enough across runs and versions to be harvested by automation.

Right now I can only prove (1) and partially prove that (2) exists in some mode/history. I cannot prove the rest for current standalone exec.
