# CodexFarm reasoning trace capture report

## What the user needs

The goal is to persist the real reasoning trace data that Codex visibly shows during CLI execution.

The current output is not good enough:

- Recipeimport benchmark prompt samples often show `_No thinking trace captured for this sample._`
- Some calls are reported as having reasoning traces only because CodexFarm heuristically matched words inside the final JSON output payload
- That heuristic output is not the real Codex reasoning trace the user wants

## Concrete failing run

Investigated run:

- `data/golden/benchmark-vs-golden/2026-03-14_17.21.15/single-offline-benchmark/saltfatacidheatcutdown/codexfarm/`

Affected artifact:

- `prompts/prompt_type_samples_from_full_prompt_log.md`

## What recipeimport is doing

Recipeimport is not inventing the missing-trace message.

Relevant code:

- `recipeimport/cookimport/cli.py` reads `thinking_trace.reasoning_events`
- it prints `_No thinking trace captured for this sample._` only when `thinking_trace.available` is false and no excerpt exists

Recipeimport trusts the CodexFarm `.trace.json` artifact and `codex_exec_activity.csv`. It is downstream of the bug.

## What was found in CodexFarm artifacts

Relevant CodexFarm code:

- `src/codex_farm/codex_exec.py`
- `_parse_jsonl_events(...)`
- `_event_matches_trace_hints(...)`
- `_persist_trace_artifact(...)`

For the full `2026-03-14_17.21.15` Salt Fat Acid Heat CodexFarm run:

- `195` trace files were inspected
- all `195` had `item.type = "agent_message"` in the final `item.completed` event
- `0` had a real nested `item.type = "reasoning"` event
- `29` still recorded `reasoning_event_count > 0`

That means the nonzero reasoning counts are currently false positives.

## Raw event shape observed

The raw event stream in affected `.trace.json` files was consistently:

```json
{"type":"thread.started", ...}
{"type":"turn.started"}
{"type":"item.completed","item":{"type":"agent_message","text":"{...final JSON output...}"}}
{"type":"turn.completed","usage":{...}}
```

No separate reasoning event was present in those persisted JSON events.

## Why counts are currently wrong

Current reasoning classification in `src/codex_farm/codex_exec.py` uses heuristic substring matching:

- reasoning type hints: `reason`, `thinking`, `analysis`, `deliberat`
- reasoning key hints: `reasoning`, `thinking`, `analysis`, `deliberat`

This causes false positives:

- pass1 chunking rows were counted as reasoning because the final JSON payload contained `reasoning_tags`
- one pass4 row was counted as reasoning because snippet text contained `deliberat`
- one pass4 row also matched action heuristics because snippet text contained `decision`

So current `reasoning_event_count` can mean "payload text happened to contain a hint word", not "Codex emitted reasoning trace data".

## Important distinction

There appear to be two separate problems:

1. The real reasoning trace the user sees in Codex CLI is not reaching the persisted `--json` event stream / trace artifact used by CodexFarm.
2. CodexFarm then tries to recover "reasoning" using content heuristics over final `agent_message` output, which creates misleading fake positives.

## Most likely break surface

The key question for CodexFarm is:

Why is the real Codex reasoning data visible in the interactive CLI experience not being captured in the machine-readable artifacts?

Based on this investigation, likely possibilities are:

- `codex exec --json` is not currently exposing the reasoning stream Codex shows interactively
- CodexFarm is invoking the wrong mode/flags/surface for reasoning-trace capture
- Codex reasoning is being emitted somewhere other than the captured stdout JSON event stream
- there is another artifact or side channel available from Codex that CodexFarm is not harvesting

The bug does **not** look like JSON-event parsing loss inside CodexFarm after stdout capture:

- `_parse_jsonl_events(...)` preserved the four JSON events it received
- `.trace.json` saved those events faithfully

So the missing real reasoning data is likely absent before or during CodexFarm capture, not dropped later by recipeimport.

## What the maintainer should fix

### Required outcome

CodexFarm should persist the real reasoning trace data the user can already see during Codex execution, not a heuristic guess derived from the final output payload.

### Minimum fixes

1. Stop treating ordinary final `item.completed` `agent_message` payload text as reasoning/action trace evidence.
2. Find the actual Codex surface that exposes reasoning traces for non-interactive execution and persist that data directly.
3. Make `reasoning_event_count` mean real captured reasoning events only.
4. If the chosen Codex execution surface truly does not expose reasoning traces, record that explicitly instead of synthesizing fake positives.

### Strongly suggested debugging steps

1. Reproduce one failing `codex exec --json` call outside the worker with the exact same arguments CodexFarm used.
2. Compare:
   - interactive CLI-visible reasoning
   - stdout JSON events
   - stderr
   - any temp/output files
   - any Codex home/session logs
3. Determine where the reasoning UI data actually lives.
4. Persist that source directly into `.trace.json` and `codex_exec_activity.csv`.

## Evidence summary

From recipeimport run artifacts:

- `pass1`: `23/23` rows showed `reasoning_event_count = 1`, but this was caused by `reasoning_tags` in final payload text
- `pass2`: `23/23` rows showed `reasoning_event_count = 0`
- `pass4`: `29` rows showed nonzero counts only when payload text accidentally matched heuristic hint words

This pattern is inconsistent with a real reasoning-trace capture surface and consistent with heuristic misclassification.

## Bottom line

The user is correct to expect real reasoning trace data to exist somewhere, because Codex visibly shows it during execution. The current CodexFarm trace artifacts are not capturing that real data. Instead, they currently mix:

- genuine absence of captured reasoning events in persisted JSON traces, and
- false-positive reasoning counts inferred from normal final output payload text.

The maintainer should fix capture first, and remove heuristic fake positives so the artifact truth is reliable.
