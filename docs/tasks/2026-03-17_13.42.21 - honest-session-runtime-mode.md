# Honest Session Runtime Mode

## Problem statement

`codex-farm process` only told the truth about task farming, not about persistent Codex session reuse. External callers such as RecipeImport needed a first-class runtime mode that actually reuses one Codex session across multiple queued tasks and reports that behavior in machine-readable outputs.

## Acceptance criteria

- `process`, `run create`, and `go` accept and persist `--runtime-mode`.
- `structured_loop_agentic_v1` defaults to one worker and rejects `--workers > 1`.
- Agentic runs can boot one Codex session, resume it for later tasks, and persist session/task linkage in SQLite and `.codex-farm-sessions/`.
- `process --json`, progress snapshots, telemetry summaries, and docs expose additive session-aware fields without breaking classic mode.

## Evidence

- Full `pytest -q` passed after the change.
- Focused process smoke proves `structured_loop_agentic_v1` reuses one session across multiple tasks and rejects multi-worker requests.
- Real `codex exec` plus `codex exec resume` smoke returned `{"ok":1}` then `{"ok":2}` from the same session key.

## Constraints and decision

- `codex exec resume` does not expose per-turn `--output-schema`, `--cd`, or `--model`, so agentic mode freezes session-level execution context and validates resumed payloads locally.
- The implementation stores a neutral `resume_key` alongside `thread_id` and currently uses the observed `thread.started.thread_id` because that worked in the live smoke.
- First release scope stays intentionally narrow: agentic mode is single-worker only, and `recipeimport_benchmark_mode` is rejected there rather than papering over unsupported semantics.

## Rollback / compensation

If agentic behavior causes trouble, revert to `classic_task_farm_v1` for equivalent runs. The change is additive at the CLI and schema level, so classic one-shot processing remains the safe fallback path.
