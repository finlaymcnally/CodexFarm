summary: "RecipeImport currently receives CodexFarm `process --json` results only after subprocess completion, so CodexFarm needs an explicit machine progress surface for spinner integration."
read_when:
  - "When adding caller-facing progress APIs/events for external CodexFarm integrations"
  - "When integrating RecipeImport spinner/progress UX with CodexFarm runtime state"
---

- RecipeImport currently invokes CodexFarm via blocking `subprocess.run(..., capture_output=True)` in `cookimport/llm/codex_farm_runner.py`, so it cannot observe live state from stdout/stderr without changing to streaming subprocess handling.
- RecipeImport spinner plumbing already supports machine-prefixed progress payloads (`__worker_activity__ ...`) and callback-based rendering, so a prefixed CodexFarm event line contract is a good fit.
- Existing CodexFarm `process --json` contract must keep stdout as a single parseable payload; progress state therefore belongs on a separate channel (`run progress --json` polling and/or stderr-prefixed events).
