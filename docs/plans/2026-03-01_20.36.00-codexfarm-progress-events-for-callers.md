# Add machine-readable CodexFarm run progress snapshots/events

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds.

`docs/PLANS.md` is checked in and this plan is maintained in accordance with it.

## Purpose / Big Picture

External callers (starting with RecipeImport) can already run `codex-farm process --json`, but they only get one final JSON payload at the end. After this change, callers can also consume machine-readable run progress while work is in flight, so spinner/progress UIs can show real CodexFarm state instead of generic phase text.

The user-visible outcome is twofold: a new `run progress` command that returns a structured snapshot (and optional watch stream), and a `process` flag that emits structured progress events on stderr without breaking JSON stdout contracts.

## Surprises & Discoveries

- Observation: RecipeImport currently calls CodexFarm with blocking `subprocess.run(..., capture_output=True)` in `cookimport/llm/codex_farm_runner.py`, so its current integration only receives final stdout/stderr once `process` exits.
  Evidence: reviewed RecipeImport runner implementation during this task.
- Observation: the initial new test failed because mocked `run_codex_exec` accessed a non-existent `input_path` kwarg; worker-side prompt parsing is the stable source-path contract in this test seam.
  Evidence: `test_process_progress_events_emit_machine_readable_stderr` first run failed with terminal error `"Unexpected worker error: 'input_path'"`, then passed after using prompt-derived input path.

## Decision Log

- Decision: Add a dedicated `run progress` API and a separate `process` progress-event flag rather than changing default stderr output format.
  Rationale: preserves backwards compatibility while offering an opt-in machine contract for callers.
  Date/Author: 2026-03-01 / Codex CLI agent
- Decision: Use a fixed stderr prefix (`__codex_farm_progress__ `) and compact per-line JSON payloads for event streaming.
  Rationale: external callers can safely filter/parse event lines without disturbing existing human stderr output or final stdout JSON parsing.
  Date/Author: 2026-03-01 / Codex CLI agent

## Context and Orientation

`src/codex_farm/cli.py` owns command contracts and process orchestration. `src/codex_farm/db.py` owns run/task query helpers used by CLI commands. Existing run visibility commands are `run status`, `run tasks`, and `run errors`; none currently package a single spinner-oriented snapshot with running-task detail and completion percentages. `process --json` must keep stdout machine-clean (single final JSON payload), so any streaming progress must go to stderr.

## Plan of Work

Add small DB read helpers for "currently running tasks" and "recent error tasks". Build a reusable progress snapshot payload helper in `cli.py` that combines run status counts, completion math, running-task rows, and recent-error rows. Expose it as `run progress` with single-shot JSON/text and optional `--watch` polling mode.

Then extend `process` with an opt-in progress event flag that emits prefixed JSON events to stderr (start/progress/finish) while workers run, wired through `_run_workers` via a callback so the polling loop can emit snapshots at its existing cadence.

## Idempotence and Recovery

This change is additive and non-destructive. If event output shape needs rollback, callers can stop using `--progress-events` and continue using existing `process --json` contracts unchanged.

## Artifacts and Notes
