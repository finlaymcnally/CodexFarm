# Isolate Recipe Codex Execution Context

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds.

This document follows `docs/PLANS.md` and must be maintained in accordance with that file.

## Purpose / Big Picture

After this change, recipe-oriented runs in CodexFarm will execute `codex exec` from a sterile scratch directory outside the repository, and they can optionally use a dedicated Codex home directory through the `CODEX_HOME` environment variable. The user-visible result is that recipe jobs stop inheriting repo-local coding instructions such as `AGENTS.md`, so reasoning traces and token spend stay focused on the recipe payload instead of repo onboarding behavior. You can see it working by running a recipe pipeline and verifying that the effective `--cd` path is a scratch directory under `var/`, not the repo root, while the output JSON and retry behavior remain unchanged.

## Surprises & Discoveries

- Observation: the main recipe prompts are already self-contained because `render_prompt_template(...)` in `src/codex_farm/pipeline_spec.py` substitutes `{{INPUT_TEXT}}` directly from the input file.
  Evidence: `pipelines/recipe.schemaorg.normalize.v1.json` and `pipelines/recipeimport.benchmark.line_label.v1.json` both set `"prompt_input_mode": "inline"`.
- Observation: the leak is caused by execution context, not prompt wording. The prompt says to use only the payload, but the model still starts inside a repo containing coding-agent instructions.
  Evidence: `src/codex_farm/worker.py` resolves `asset_root` to `farm_root`, and `src/codex_farm/codex_exec.py` always passes that resolved path as `codex exec --cd`.
- Observation: a generic unscoped worker cannot know a single correct `CODEX_HOME` value ahead of time if it may lease runs with different stored execution homes.
  Evidence: `worker` precheck currently runs before leasing starts, while run-specific config is only available after the worker opens the database and inspects a specific run or claimed task.
- Observation: scratch execution must bypass even an explicit `workspace_root` at subprocess time, otherwise recipe runs still inherit the caller-selected project directory.
  Evidence: after recipe pipelines switched to `codex_execution_context="scratch"`, worker tests that previously asserted `workspace_root` as the real `--cd` had to be updated to expect `<data_dir>/execution_contexts/...` instead.

## Decision Log

- Decision: make workspace isolation a pipeline-level default instead of relying only on ad hoc CLI flags.
  Rationale: the bug is tied to the nature of recipe pipelines, not to a single user command. A pipeline default prevents accidental regressions when the same pipeline is run through `one`, `process`, `go`, or resumed workers.
  Date/Author: 2026-03-13 / Codex

- Decision: keep scratch workspaces empty by default and do not write an extra `AGENTS.md` into them.
  Rationale: the goal is to remove instruction bleed-through, not replace it with another layer of guidance. Recipe prompts are already inline and sufficient for task definition.
  Date/Author: 2026-03-13 / Codex

- Decision: support a dedicated `CODEX_HOME` as an execution override, but treat the sterile scratch `--cd` directory as the primary fix.
  Rationale: the observed leak is definitely caused by repo-local context. A separate Codex home is still worthwhile defense-in-depth and is necessary if home-scoped Codex settings or session state must differ between coding and recipe modes.
  Date/Author: 2026-03-13 / Codex

- Decision: preserve the existing generic worker precheck for unscoped workers, but teach `one`, `process`, `go`, and `worker --run-id` to precheck the resolved recipe Codex home.
  Rationale: an unscoped worker may legally process multiple runs with different stored home paths. A single precheck cannot prove all of them. Scoped commands can and should preflight the exact home they will use.
  Date/Author: 2026-03-13 / Codex

## Outcomes & Retrospective

Implemented on 2026-03-13. Recipe-oriented pipelines now declare `codex_execution_context="scratch"` and `codex_home_profile="recipe"`, run-based commands persist resolved `codex_home_path`, and runtime execution uses sterile per-attempt directories under `<data_dir>/execution_contexts/` plus optional `CODEX_HOME` env overrides. The remaining gap is operational rather than architectural: a user still needs to create and authenticate the dedicated recipe `CODEX_HOME` once before real recipe runs can use it.

## Context and Orientation

CodexFarm is a local CLI orchestrator that stores runs in SQLite, freezes prompt/schema assets for deterministic execution, and calls `codex exec` through one subprocess wrapper. The relevant files are:

`src/codex_farm/pipeline_spec.py` defines the pipeline JSON schema and loads pipeline files from `pipelines/*.json`. This is where new per-pipeline execution-context fields must be defined.

`src/codex_farm/cli.py` is the main command entrypoint. `one` executes a single task immediately. `run create` and `process` create persisted runs. `go` is the guided wrapper over the same runtime pieces. This file also runs the Codex precheck before execution starts.

`src/codex_farm/run_assets.py` freezes the effective pipeline configuration into `var/run_assets/<run_id>/effective_pipeline.json`. Any execution knob that must survive resumed workers belongs either in this frozen file or in `runs.config_json`.

`src/codex_farm/worker.py` claims tasks, resolves the effective execution configuration, renders prompts, and calls `run_codex_exec(...)`. It currently chooses the actual working directory through `_resolve_task_cd_dir(...)`.

`src/codex_farm/codex_exec.py` assembles the `codex exec` command and calls `subprocess.run(...)`. It is the only place that can reliably inject a custom subprocess environment such as `CODEX_HOME`.

`src/codex_farm/heads_up.py` performs post-run learning by sending a summary payload back through `run_codex_exec(...)`. If a recipe run uses the isolated profile, that learning pass should use the same isolated execution context so it does not reintroduce repo bleed-through.

In this plan, a “sterile scratch workspace” means a temporary directory outside the repository tree, with no repo `AGENTS.md`, no prompt/template files, and no user code. A “Codex home” means the directory pointed to by the `CODEX_HOME` environment variable. Codex may use that directory for local profile, auth, or other home-scoped state, so using a separate home isolates recipe execution from coding-session state.

## Milestone 1: Teach pipelines and runs how to describe isolated execution

At the end of this milestone, a recipe pipeline can declare that it should run in a scratch execution context, and run creation will persist enough information for resumed workers to keep using that context. Nothing will yet create scratch directories or alter the subprocess environment, but the configuration model will be complete and testable.

Edit `src/codex_farm/pipeline_spec.py` to add a new plain-language field that describes where Codex should run. Use `codex_execution_context` with allowed values `"project"` and `"scratch"`, defaulting to `"project"`. Keep `codex_cd_mode` unchanged for the project case. Also add `codex_home_profile: str | None = None` so a pipeline can request a named home profile such as `"recipe"` without hardcoding a user-specific absolute path into the repository.

Update `PipelineSpec`, `PipelineSpecModel`, and any parsing tests in `tests/test_pipeline_spec.py` and `tests/test_pack_lint.py` to cover the new fields. Then update the recipe-oriented pipeline files in `pipelines/recipe.schemaorg.normalize.v1.json`, `pipelines/recipe.schemaorg.to_proprietary.v1.json`, and `pipelines/recipeimport.benchmark.line_label.v1.json` so they declare `"codex_execution_context": "scratch"` and `"codex_home_profile": "recipe"`.

Edit `src/codex_farm/run_assets.py` so `FrozenExecutionSpec` and the serialized `effective_pipeline.json` include `codex_execution_context` and `codex_home_profile`. That keeps resumed workers deterministic even if a pipeline file later changes. Persist the resolved absolute Codex home path separately in `runs.config_json`, because that path is user-local and may come from a CLI flag or environment variable at run creation time.

Update the run-creation code in `src/codex_farm/cli.py` so `run create`, `process`, and `go` resolve the Codex home path once and persist it in `config_json` when present. The resolution order should be: explicit CLI `--codex-home` path if provided, otherwise environment variable derived from the pipeline profile name, otherwise no override. For the profile mapping, use `CODEX_FARM_CODEX_HOME_<PROFILE>` where `<PROFILE>` is uppercased and non-alphanumeric characters are converted to underscores. For the recipe profile this means `CODEX_FARM_CODEX_HOME_RECIPE`.

Acceptance for this milestone is straightforward. New parsing tests should pass, frozen run assets should contain the new logical fields, and the JSON payload from `run create --json` should show the resolved execution context and the stored Codex home path or `null`.

## Milestone 2: Centralize runtime preparation of scratch workspaces and subprocess environment

At the end of this milestone, there will be one helper that converts the logical execution settings into concrete runtime inputs: the actual `--cd` directory, the optional `CODEX_HOME` override, and cleanup instructions.

Create a new module `src/codex_farm/execution_context.py`. Define a small dataclass such as `PreparedExecutionContext` with `cd_dir: Path`, `env_overrides: dict[str, str]`, `scratch_root: Path | None`, and a concise metadata dictionary suitable for forensics or telemetry. Also define one function, for example `prepare_execution_context(...)`, that receives the logical execution context, the existing project `cd_dir`, the resolved data directory, run/task identity, and the resolved Codex home path from run config.

When `codex_execution_context == "project"`, return the original `cd_dir` unchanged and an empty `env_overrides` mapping unless a Codex home path was explicitly resolved. When `codex_execution_context == "scratch"`, create a per-attempt directory under `var/execution_contexts/`. For workers, the directory must include `run_id`, `task_id`, and `lease_token` so retries never collide. For `one`, include a timestamp and a short UUID. The scratch directory should be empty except for an optional tiny marker file such as `context.json` if that helps debugging. Do not create an `AGENTS.md`.

Then edit `src/codex_farm/codex_exec.py` so `run_codex_exec(...)` accepts `env_overrides: Mapping[str, str] | None = None`. Merge overrides on top of `os.environ.copy()` and pass the merged dictionary to `subprocess.run(...)`. This function should not try to understand what `CODEX_HOME` means; it only receives the prepared environment.

Also extend the trace and telemetry surfaces in `src/codex_farm/codex_exec.py` so debugging can prove the isolation is active. Add additive telemetry columns for `execution_context` and `codex_home_path`. Include those same values in the trace artifact and in forensics runtime context. This is local tooling and already records prompt text and filesystem paths, so absolute path visibility is acceptable here.

Acceptance for this milestone is a focused test in `tests/test_codex_exec.py` that monkeypatches `subprocess.run(...)` and asserts that the command still contains the expected `--cd`, while the subprocess environment contains the injected `CODEX_HOME` value when present.

## Milestone 3: Use the prepared context in one-shot, worker, and Heads Up paths

At the end of this milestone, all recipe-oriented execution entrypoints will actually run from a scratch directory instead of the repo root.

Edit `src/codex_farm/cli.py` in the `one` command. Resolve the logical execution context from the selected pipeline plus any explicit `--codex-home` override. Prepare the execution context immediately before calling `run_codex_exec(...)`, pass `prepared.cd_dir` instead of the current `cd_dir`, and pass `prepared.env_overrides` into the new subprocess parameter. Ensure the one-shot forensics runtime context records both the logical execution context and the effective scratch directory path. Clean up the scratch directory after execution and after best-effort forensics capture, using `shutil.rmtree(..., ignore_errors=True)` so cleanup never changes success or failure semantics.

Edit `src/codex_farm/worker.py` so worker execution uses the same helper. The worker already knows `run_id`, `task_id`, `lease_token`, `data_dir`, the resolved farm root, and the project-style `cd_dir`. Add `codex_execution_context` to the resolved execution contract. Read the resolved absolute Codex home path from `runs.config_json`. Prepare the execution context per attempt, pass it into `run_codex_exec(...)`, and clean it up after the attempt is finalized. For retry safety, create a new scratch directory every attempt rather than reusing one across retries.

Edit `src/codex_farm/heads_up.py` so post-run learning uses the same isolation when the originating run says it should. The simplest way is to make the caller hand `learn_heads_up_from_run(...)` the needed run config fields or let the helper load them. The important rule is that a recipe run should not finish with a clean main task path and then perform its learning call back in the repo root.

Update `src/codex_farm/cli.py` JSON output surfaces for `run create --json` and `process --json` with additive fields that make the chosen execution context visible. Use names like `codex_execution_context` and `codex_home_path`. Existing callers should keep working because the schema expands additively.

Acceptance for this milestone is an end-to-end fake-Codex integration test. Extend `tests/test_fake_codex_pipeline_pack_demo.py` or add a new focused test that captures the actual `--cd` argument and the `CODEX_HOME` environment seen by the fake `codex` executable. For a recipe-style pipeline, the asserted `--cd` path must live under the run data directory and must not equal the pack root.

## Plan of Work

Begin by extending the pipeline schema and run snapshot model, because the runtime should not gain new behavior until the configuration is explicit and persistent. Once the new fields are in place, add the central execution-context helper module so the worker, one-shot, and Heads Up paths do not each invent their own scratch-directory logic.

Then wire the helper into `one`, `worker`, and Heads Up learning, in that order. `one` is the smallest execution path and provides the quickest proof that scratch isolation works before touching retries and leased workers.

Only after the real execution paths are working should you update prechecks. Scoped commands can preflight the correct `CODEX_HOME`; mixed-run workers cannot. Finally, refresh the docs and add one final discovery note if implementation reveals a nuance that was not obvious during planning.

## Idempotence and Recovery

This plan is intentionally additive. New pipeline fields default to the existing project behavior, so older pipelines keep working until explicitly switched to scratch mode. Scratch directories live under `var/` and can be deleted safely when no runs are active. Their names include run and attempt identity so retries and reruns do not collide.

If a command fails halfway through scratch workspace creation, retrying is safe because the runtime should create a fresh directory with a unique suffix. If a run is created with the wrong Codex home path, do not mutate the existing run in place. Instead, fix the environment or CLI argument and create a new run so the stored execution contract stays trustworthy.

If the dedicated recipe home becomes corrupted or signed out, run the login command again with the same `CODEX_HOME` path. Do not copy the main coding home into it; the whole point is to keep recipe execution isolated.
