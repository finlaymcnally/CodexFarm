# Harvest Rollout Thinking Traces

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds.

This document follows `docs/PLANS.md` and must be maintained in accordance with that file.

## Purpose / Big Picture

After this change, CodexFarm will stop treating “missing thinking trace” as one undifferentiated failure. For each `codex exec` call it will tell the truth about what happened: whether stdout had explicit reasoning events, whether a rollout file existed for the returned thread id, whether that rollout contained reasoning items, whether those items had human-readable summaries, and whether only encrypted reasoning was present. When summary text exists, users inspecting `.trace.json`, telemetry, or downstream prompt exports will be able to see it. When summary text does not exist, the artifact will say that explicitly instead of looking like CodexFarm simply failed to record anything.

The user-visible success case is easy to verify. Run one CodexFarm task, open the saved `.trace.json`, and inspect a new normalized reasoning section. It should tell you one of a few plain-language statuses such as `stdout_reasoning_present`, `rollout_summary_present`, `rollout_summary_empty_encrypted_present`, or `rollout_missing`. For runs where rollout summaries are available, the saved reasoning excerpt should be visible without needing to inspect raw session files manually.

## Decision Log

- Decision: treat rollout files as the primary rich reasoning surface, while keeping stdout JSONL as the primary explicit event stream.
  Rationale: local evidence now shows that stdout often has no reasoning events while the matching rollout file still contains real reasoning metadata and token counts.
  Date/Author: 2026-03-16 / Codex

- Decision: do not attempt to decrypt `encrypted_content`.
  Rationale: CodexFarm should harvest supported plain-text surfaces and metadata truthfully; trying to reverse or guess encrypted reasoning would be brittle and likely inappropriate.
  Date/Author: 2026-03-16 / Codex

- Decision: add explicit state classification for rollout results instead of collapsing everything into “reasoning_event_count = 0”.
  Rationale: users need to distinguish “no rollout found” from “rollout found but summary empty” from “summary present”.
  Date/Author: 2026-03-16 / Codex

- Decision: prototype any summary-enabling Codex config before wiring it into production execution.
  Rationale: the current machine evidence proves that rollout harvesting is useful now, but it does not yet prove that any available config knob will restore human-readable summaries.
  Date/Author: 2026-03-16 / Codex

- Decision: do not add a production `model_reasoning_summary` override path for `gpt-5.3-codex-spark`.
  Rationale: the live probe failed with `unsupported_parameter`, so shipping that flag would break the current affected model instead of restoring summaries.
  Date/Author: 2026-03-16 / Codex

## Outcomes & Retrospective

Implemented. CodexFarm now harvests rollout reasoning metadata by thread id, persists that result into both trace artifacts and telemetry, and exposes a normalized `captured_reasoning` block so downstream consumers can tell the difference between stdout reasoning, rollout summary text, empty-summary encrypted rollout metadata, missing rollouts, and missing thread ids. The remaining limitation is upstream/model-side: current `gpt-5.3-codex-spark` runs still often produce empty rollout summaries, and the direct `model_reasoning_summary` probe failed with `unsupported_parameter`, so the honest shipped behavior is classification rather than synthetic restoration.

## Context and Orientation

`src/codex_farm/codex_exec.py` is the only execution seam that sees every `codex exec` call. It already:

- builds the subprocess command,
- parses stdout JSONL into events,
- extracts `thread.started.thread_id`,
- writes `.trace.json` artifacts,
- and appends rows to `codex_exec_activity.csv`.

Right now it does not do anything with the returned thread id beyond telemetry. It also does not inspect rollout/session files at all. That is the missing bridge.

A “rollout file” in this plan means a JSONL file under `CODEX_HOME/sessions/YYYY/MM/DD/rollout-*.jsonl` that stores richer local Codex execution state than public stdout JSONL. In current local evidence, these files can contain:

- `response_item` rows with `payload.type = "reasoning"`
- `payload.summary` (sometimes empty, sometimes a list of summary objects)
- older plain-language `summary_text` entries on historical runs
- `payload.encrypted_content`
- `event_msg` rows whose token payload can include `reasoning_output_tokens`

A “normalized reasoning block” in this plan means a small plain-language structure in the saved trace artifact that downstream tools can trust without knowing Codex rollout internals. It should say where the reasoning came from and whether it is actually readable.

## Milestone 1: Add rollout discovery and parsing

At the end of this milestone, CodexFarm will be able to take a thread id plus an effective Codex home path and answer a precise question: “Did a rollout file exist for this run, and if so what reasoning metadata did it contain?”

Create a small helper module, for example `src/codex_farm/rollout_reasoning.py`, to keep filesystem parsing out of the main subprocess wrapper. Define a dataclass such as:

    @dataclass(frozen=True)
    class RolloutReasoningResult:
        status: str
        thread_id: str | None
        codex_home_path: Path | None
        rollout_path: Path | None
        reasoning_item_count: int
        summary_count: int
        summary_texts: list[str]
        encrypted_reasoning_present: bool
        reasoning_output_tokens: int | None
        recorder_error_detected: bool

Also define one public function, for example:

    def harvest_rollout_reasoning(
        *,
        thread_id: str | None,
        codex_home_path: Path | None,
        stderr_text: str,
    ) -> RolloutReasoningResult:
        ...

Implementation rules:

- If `thread_id` is missing, return `status="thread_missing"`.
- Resolve the effective home path using `CODEX_HOME` when present, otherwise `Path.home() / ".codex"`.
- Search `sessions/**/*.jsonl` directly by thread id in filename and, if needed, by content match.
- If no rollout file is found, return `status="rollout_missing"`.
- If a rollout file is found but contains no `payload.type = "reasoning"`, return `status="reasoning_missing"`.
- Normalize human-readable summary text from both shapes seen locally:
  - older entries with a direct `summary_text` field
  - newer `payload.summary` arrays whose items may carry text-like fields
- If reasoning exists and at least one human-readable summary string is present after normalization, return `status="summary_present"`.
- If reasoning exists but `summary` is empty and `encrypted_content` is present, return `status="summary_empty_encrypted_present"`.
- Detect recorder failures from stderr patterns like `failed to record rollout items` and reflect that in `recorder_error_detected`, but do not let that override a real found rollout file.

Acceptance for this milestone is a focused test module or expanded `tests/test_codex_exec.py` coverage that feeds sample rollout JSONL files and asserts each status branch.

## Milestone 2: Persist normalized rollout reasoning in trace artifacts and telemetry

At the end of this milestone, every CodexFarm trace artifact and telemetry row will say not just “reasoning_event_count,” but also what rollout harvesting found.

Edit `src/codex_farm/codex_exec.py` so `run_codex_exec(...)`:

1. extracts `thread_id` from stdout events,
2. resolves the effective Codex home path from `env_overrides.get("CODEX_HOME")` or the default home,
3. calls `harvest_rollout_reasoning(...)`,
4. writes the returned information into both `.trace.json` and `codex_exec_activity.csv`.

Add an explicit normalized block to the trace artifact, for example:

    "captured_reasoning": {
      "status": "summary_present",
      "source": "rollout_summary",
      "thread_id": "...",
      "rollout_path": "...",
      "summary_texts": ["..."],
      "reasoning_output_tokens": 445,
      "encrypted_reasoning_present": true,
      "recorder_error_detected": false
    }

Keep the existing `reasoning_events` fields as the stdout-explicit event slice. Do not silently repurpose them. The new normalized block is the truth layer that downstream consumers should inspect when they want human-readable thinking.

Additive telemetry columns should include at least:

- `rollout_reasoning_status`
- `rollout_path`
- `rollout_reasoning_item_count`
- `rollout_reasoning_summary_count`
- `rollout_reasoning_output_tokens`
- `rollout_encrypted_reasoning_present`
- `rollout_recorder_error_detected`

If useful for local debugging, also add a short JSON cell such as `rollout_reasoning_summary_texts_json`.

Acceptance for this milestone is a test that simulates one exec run, writes a fake rollout file, and asserts that both trace JSON and telemetry CSV include the expected rollout reasoning fields.

## Milestone 3: Expose a downstream-friendly thinking-trace contract

At the end of this milestone, users and downstream tools will not have to understand Codex rollout internals to know whether “thinking” was actually captured.

Define a small, stable contract in the trace artifact and docs that answers:

- Was any reasoning captured?
- Was it captured from stdout or from rollout summary text?
- If reasoning existed but only encrypted content was present, what exactly was missing?

Use clear statuses such as:

- `stdout_reasoning_present`
- `rollout_summary_present`
- `rollout_summary_empty_encrypted_present`
- `rollout_missing`
- `thread_missing`
- `reasoning_missing`

If `summary_present`, include a compact excerpt or the full list of summary text blocks in the normalized reasoning block. If not, include an explanatory `note` field so prompt exporters and dashboards can say “reasoning existed but Codex provided no human-readable summary” rather than “no thinking trace captured.”

Update docs so callers know the difference between:

- stdout explicit reasoning events (`reasoning_events`)
- rollout-backed normalized thinking (`captured_reasoning`)

Acceptance for this milestone is an updated trace artifact example in docs plus tests covering `summary_present` and `summary_empty_encrypted_present`.

## Plan of Work

Start by building the smallest possible rollout parser in a separate helper module and driving it with tests based on sampled local rollout JSONL lines. That keeps the parsing logic deterministic before threading it through the live subprocess path.

Next, wire the helper into `run_codex_exec(...)` after stdout event parsing and thread-id extraction. Once rollout results are available there, extend both trace persistence and telemetry rows. Do not change worker or CLI first; every execution entrypoint already funnels through `run_codex_exec(...)`, so rollout harvesting belongs at that shared seam.

After rollout results are being persisted, add the normalized user-facing reasoning block and update docs. Only then run the summary-enablement prototype. The prototype must be treated as a controlled branch in the plan: it may lead to a small production config feature, or it may end with “no usable summary-enablement path exists right now.”

## Idempotence and Recovery

Rollout harvesting is read-only over files already written by Codex. Re-running tests or re-running the rollout parser cannot corrupt session data. The helper should never mutate `CODEX_HOME/sessions/...`; it only reads and classifies.

If the matching rollout file cannot be found immediately, do not turn that into task failure. Treat rollout harvesting as best-effort observability and persist `rollout_missing` instead. Execution success/failure semantics must stay unchanged.

If the summary-enablement prototype shows no effect, stop there and record that result. Do not leave speculative config flags half-wired into normal execution.
